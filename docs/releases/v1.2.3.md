# ZeroLite 1.2.3

ZeroLite 1.2.3 replaces 1.1.0, 1.2.0, 1.2.1 and 1.2.2. It is the same
`zeroclaw` binary, config file and command set, on upstream **ZeroClaw
v0.8.6**, with the WASM plugin host and the web dashboard embedded.

Release builds embed the web dashboard. Platforms: Windows x64, Linux x64,
Linux arm64. No macOS build.

## 1.1.0–1.2.2 are withdrawn

Do not deploy them.

Each of those four releases did exactly one thing — merge upstream v0.8.6 —
and did it by *replacing* fork behaviour with upstream behaviour instead of
carrying the fork's decisions across. Context management is the case that
mattered: the engine that decides when to trim and what to keep was rebuilt in
upstream's shape, so the fork's water-line, its keep-N retention and its
calibration stopped existing. The config table still parsed, the binary still
built, and the test suite still went green — the suite had been written against
the new shape, so nothing in the tree could see the difference. The one visible
symptom was a trim notice on every single turn.

1.2.3 is the release where the merge is actually finished: upstream v0.8.6 as
the base, the fork's decisions preserved, and the preserved behaviour pinned by
tests that fail when it is replaced.

## The context engine is the fork's again

### When a trim happens

One trigger: replayed context tokens past the water-line,

```text
trim_threshold = min(window × trim_threshold_percent / 100,
                     window − reserve_tokens)        # reserve term omitted when unset
```

Nothing else starts a trim — not the turn count, not a message cap, not
`keep_recent_turns`. That last field is what a trim *keeps*, never what starts
one: a conversation may run for any number of turns past the preference, and
the transcript only gets shorter when the water-line is crossed.

### Two decision points, two kinds of evidence

| Decision point | Evidence | Is the estimate the trigger? |
| --- | --- | --- |
| **Pre-send**, before a request leaves | the population about to be sent; no report for it can exist yet | **yes** — the water-line is the local estimate |
| **Post-response**, after a reply lands | `usage.input_tokens` for the request just sent | **no** — without a report the estimate is not a measurement of what was billed |

The pre-send check runs before the request goes out, so no provider report for
that request exists and none can. The local estimate is the correct — and only
— evidence there; refusing to act on it would mean never trimming the request
that is about to overflow.

The post-response check runs after a reply lands and has the billed count. When
a provider omits usage, that check does not act on the estimate: it stays out
of the way unless the request could not fit at all. Then the overflow guard
fires against **`send_budget`**, not the raw window:

```text
send_budget = window − reserve_tokens        # or the full window when unset
```

A prompt that fits the window but leaves the model no room to answer in has
already failed, so the reserve is physical output space rather than a
preference; and `send_budget` is what carries `request_token_ceiling` into the
check, so a guard measured against the raw model window would ignore an
operator's declared ceiling.

### What a trim does

Keep the newest `keep_recent_turns` whole turns, then cascade down until the
retained set fits `send_budget`, then fail the turn if even one turn does not
fit. A turn is never split, and the newest turn is never dropped. The cascade
logs a warning when it lands below the preference.

### There is no context compaction

Compaction is a model call that rewrites history into a smaller surrogate and
then stores the surrogate as history. ZeroLite implements it in no form — no
summarization pass, no mid-turn compaction, no provider-side compaction hook,
and no config key that turns one on. A shrinking history is a **trim**: whole
turns are dropped, and the surviving turns remain exactly what the model
produced.

There is also no switch that turns trimming off. A disabled trim would let the
request exceed the window and fail at the provider, where the cause is no
longer visible.

Both are recorded decisions in `docs/design/context-management.md`: R6
("retention is by dropping, never by rewriting") and R7 ("there is no context
compaction in this system").

### Configuration

```toml
[runtime_profiles.coder.context]
request_token_ceiling = 100_000   # optional; clamps the effective window
trim_threshold_percent = 80       # water-line, default 80
reserve_tokens = 16_384           # output headroom, optional
keep_recent_turns = 5             # preferred whole turns, default 5 (clamped 1–10)
```

| Field | Default | Meaning |
|---|---|---|
| `request_token_ceiling` | unset | Hard ceiling on total request input tokens. Clamps the effective window (`model_window.min(ceiling)`), which is also the context meter's denominator. It does not by itself trigger trimming. |
| `trim_threshold_percent` | `80` | Percentage of the effective window at which trimming engages. Must be `1..=100`; `0` or above `100` is a hard config error. |
| `reserve_tokens` | unset | Output headroom. Bounds the water-line from above and defines `send_budget`. Must not exceed half the effective window. |
| `keep_recent_turns` | `5` | Preferred whole turns a trim retains. Clamped to `1..=10`. If they do not fit `send_budget`, the runtime cascades down to one turn. |

`[context].max_input_tokens` is still not accepted. It was renamed to
`request_token_ceiling` in 1.2.1 and 1.2.3 keeps the rename.

## `compact_context` is now `lean_bootstrap`

The runtime-profile knob that caps each injected workspace bootstrap file at
6000 characters, limits RAG recall to two chunks and skips the full Channel
Capabilities copy was called `compact_context`. It does not compact anything —
nothing is summarized and no history is rewritten — so it is now
`lean_bootstrap`.

```toml
[runtime_profiles.coder]
lean_bootstrap = false   # default true
```

The default is unchanged (`true`). The old key is **not** accepted: a config
that still writes `compact_context` is read as if the field were absent, which
means the agent silently gets the `true` default. Rename it before upgrading if
you had set it to `false`.

## `gateway.master_pair_code`

The master pairing code is present and reaches every gateway path again.

```toml
[gateway]
master_pair_code = "a-long-random-recovery-string"   # optional
```

Submitting that exact value on the pairing page (or to `POST /api/pair` /
`POST /pair`) logs the device in and mints a bearer token **without**
consuming the one-time startup/rotation code. It is reusable, so a lost device
does not need a new code. Treat it as a static secret.

The value is never printed — the startup banner says only that a recovery
credential is configured. It is inert while `gateway.require_pairing = false`,
and a master value that collides with the live one-time code consumes that
one-time slot.

The same code works under `zeroclaw service start`, not only under a standalone
`zeroclaw gateway start`: the daemon builds the pairing guard it hands the
gateway from the configuration, so both starts accept the code.

## Everything since 1.0.0

1.2.3 is the first release after 1.0.0 that keeps the fork's behaviour, so the
jump from 1.0.0 is the whole upstream v0.8.6 body plus the fork's own work.

Upstream notes: <https://github.com/zeroclaw-labs/zeroclaw/releases/tag/v0.8.6>

### From the fork

- **The context meter counts characters the way a model does.** The estimate is
  script-aware: Latin keeps the historical four-characters-per-token weight,
  while CJK, kana and Hangul characters are charged one token each. A CJK
  sentence used to be billed at roughly a third of what it costs, so the
  water-line sat below the truth and trimming engaged late.
- **The system prompt carries no date section.** The prefix stays byte-stable
  across turns, which is what provider prompt caching keys on.
- **A pairing code no longer outgrows its box.** `zeroclaw gateway get-paircode`
  sized the code inside a box hard-coded to fourteen columns; the box now
  follows the code.
- **The workspace root declares the same feature graph the crates do.** The
  v0.8.6 merge brought the per-tool features into the sub-crates but left the
  root `Cargo.toml` without them, so a root-level `--features tool-jira` (or
  `tools-saas`, `tools-compat`, …) resolved to nothing while the code behind it
  compiled fine. The root graph now matches, and the release spec asserts that
  no plugin-only feature leaks into the lean distribution.

### From upstream v0.8.6

The WASM plugin host is included in these binaries (`zeroclaw plugin list`,
`zeroclaw plugin update`). Release artifacts are built with
`--features embedded-web,plugins-wasm-cranelift` and smoke-tested for the host.

Breaking changes most likely to affect an existing ZeroLite install:

- Pairing codes default to 32 characters and reading or minting them needs the
  gateway admin token. Set `[gateway.pairing_code] length = 6, charset = "numeric"`
  for the old shape.
- Remote WSS needs `auth_token`; `[security.nevis]` is retired in favour of
  `[oidc.<alias>]`.
- `[browser] enabled = true` no longer implies the `browser` automation tool;
  set `browser.automation_enabled = true`.
- `file_download` refuses private-network hosts unless they are listed in
  `[file_download] allowed_private_hosts`.
- Full autonomy no longer overrides `always_ask`.
- The shell follows the platform default; set `runtime.shell = "sh"` or `"cmd"`
  to pin the previous choice.

## Fixed defects

- **The runtime stamped wall-clock time into the prompt at six sites.** User
  turns carried `[CURRENT DATE & TIME: …]` at ingest and that stamp was
  replayed into every later request; the delegate sub-agent prompt rendered a
  `## CRITICAL CONTEXT: CURRENT DATE` section; the channel turn-context
  preamble carried `time=`/`date=`/`weekday=`/`tz=`; and two loop paths
  prefixed the provider-facing user turn with a bare `[timestamp]`. All six
  are gone, which is what decision R1 in `docs/design/context-management.md`
  requires: the replayed prefix stays byte-stable, and the model no longer
  sees a per-turn date. Move any date guidance you rely on into `AGENTS.md`.
  Display-only strip helpers still recognise the legacy prefixes in old
  transcripts.
- **The trim breadcrumb lost its ownership across a restart.** The file-backed
  session store never persisted whether a transcript started with the synthetic
  trim breadcrumb, so a restarted process could not tell a genuine first user
  turn from machinery, and the transcript was trimmed again on every reconnect.
  The flag is now stored next to the transcript as a one-byte sidecar (`1` or
  `0`); anything else is corruption and fails closed.
- **A restored session replayed one row too few.** The same missing flag made
  the trim count the breadcrumb as a dropped message, so client replay started
  one turn late. The breadcrumb is now excluded from both the keep-N slots and
  the dropped-message count.
- **A session with no recorded breadcrumb flag was guessed at.** For a
  transcript written before the sidecar existed, the loader inferred "a
  breadcrumb is present" from the position of the leading row. The cap can
  leave a genuine user turn in that position, so the guess could claim
  machinery the session never had. Provenance now resolves to `false` when
  there is no record, on both the load path and the per-turn path; the next
  trim writes the flag, so the guess never has to happen again.
- **A failed Edge TTS read left its temp file behind.** The temp file, the
  spawned child and the hardened output are now owned by one RAII guard, so
  every failure path reaps before it deletes.
- **A process that had already exited was reported as alive.** The descendant
  check used a signal probe, which also succeeds for an unreaped zombie. It now
  reads the process state from the kernel.
- **The dashboard's session-lifecycle test suite could not mount.** The test
  harness did not expose `getBoundingClientRect`, which the transcript pane
  reads; mounting threw and the whole suite failed at once. The harness now
  covers that surface, and a test asserts it keeps pace with the pane.

## Upgrading from 1.0.0

- Rename `[context].max_input_tokens` to `[context].request_token_ceiling`; the
  old key is not accepted.
- `[runtime_profiles.<alias>].compact_context` is now `lean_bootstrap` and the
  old key is not accepted. If you had set it to `false`, rename it; otherwise
  the agent silently falls back to the `true` default.
- If you relied on the runtime putting today's date in the prompt, move that
  into `AGENTS.md`. Nothing in the runtime stamps a date any more.
- If you parse structured logs, the channel overflow event's attribute is
  `history_trimmed` (was `history_compacted`) and the user-facing message says
  "I trimmed recent history".
- Review the upstream breaking changes above before rolling out.
- The binary name, config path and command set are unchanged.
