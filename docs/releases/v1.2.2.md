# ZeroLite 1.2.2

ZeroLite 1.2.2 is a maintenance release over 1.2.1. It ships the same
`zeroclaw` binary, config file and command set, on upstream **ZeroClaw
v0.8.6**, with the WASM plugin host and the web dashboard embedded.

Release builds embed the web dashboard. Platforms: Windows x64, Linux x64,
Linux arm64. No macOS build.

## What changed since 1.2.1

### `gateway.master_pair_code` works again

Setting a master pairing code had no effect: the field was gone from the
config schema, so the gateway had nothing to compare a submitted code
against. The whole feature — the config key, the pairing guard's master-code
path, and both pairing endpoints — was restored.

```toml
[gateway]
master_pair_code = "a-long-random-recovery-string"   # optional
```

Submitting that exact value on the pairing page (or to `POST /api/pair` /
`POST /pair`) logs the device in and mints a bearer token **without**
consuming the one-time startup/rotation code. It is reusable, so a lost
device does not need a new code. Treat it as a static secret: prefer a long,
high-entropy value and keep it out of version control.

The value is never printed — the startup banner says only that a recovery
credential is configured. The master code is inert while
`gateway.require_pairing = false` (pairing is off, so there is no gate to
bypass), and a master value that collides with the live one-time code
consumes that one-time slot, so the shared value cannot stay permanently
redeemable.

#### The master code also works under `zeroclaw service start`

The restoration above reached the gateway, but a daemon-hosted gateway still
rejected the code: the daemon builds the pairing authority it hands the
gateway, and it built it without the configured master code, so `try_master`
found nothing to compare against and fell through to the one-time-code path.
The pairing page answered *"Invalid or expired pairing code"* for a correct,
configured value.

The same binary behaved two ways because the two starts build the guard
differently: a standalone `zeroclaw gateway start` has no daemon and builds
its own guard from the configuration (master code worked), while
`zeroclaw service start` adopted the daemon's guard (it did not). The daemon
now builds that guard from the configuration too, and both starts are pinned
by tests.

### The context engine's trim action says what it does

The trim API had grown a name that described a capability it does not have:
"trim to a token budget". The action the spec describes is *"keep the
newest `keep_recent_turns` whole turns, then cascade down until the retained
set fits `send_budget`"*, and the two are different things — the first
names a fit target, the second a retention preference plus a fit target.

`trim_to_budget` is gone from the tree, replaced by `trim_to_fit`
(`trim_conversation_to_fit` for durable history). Nothing about the
observable behaviour changes; the name now matches the contract.

Three points in that action were settled while the fork's own behaviour was
restored:

- **The hard floor is the model's capacity, not the send budget.** A
  retention that misses the send budget but still fits the model's window is
  a *soft floor*: the newest turn is dispatched rather than rejected. Only a
  population the model cannot take is an unsatisfiable floor.
- **The pre-dispatch guard trims before sending.** Whether the provider would
  accept a request is knowable locally, so the guard checks it and trims
  first, instead of discovering the answer by having the provider reject the
  request and wasting a round trip. The recovery cascade remains as the
  fallback for what the local estimate cannot see — a real image's cost,
  one-time tool schemas.
- **A provider that reports no usage no longer trims on a guess.** The
  trigger reads the provider-reported `input_tokens`, which is authoritative
  because it is what the provider billed. Many endpoints report no usage at
  all (OpenAI-compatible servers, local runtimes, some streaming responses).
  Without a reported count the runtime has no authoritative number, and the
  local estimate is not a substitute for it — so it neither trims
  proactively nor records a breadcrumb it cannot justify. It only acts as an
  overflow guard when the estimate says the request cannot fit the model
  window at all, and it skips that guard when there is no whole turn left to
  drop, because trimming could not make the request any smaller.

### The context meter counts characters the way a model does

The local token estimate priced every script the same way — roughly four
characters per token, counted over UTF-8 bytes. That is right for Latin text
and wrong for Chinese, Japanese and Korean, where a character is close to a
token. A CJK sentence was billed at a third of what it actually costs, so the
water-line sat well below the truth and trimming engaged late.

The estimate is now script-aware: Latin keeps the historical four-characters-
per-token weight, and CJK, kana and Hangul characters are charged one token
each. The text around an image is priced with the same rule as any other
message, so a CJK caption costs the same whether or not an image rides along
with it.

### The runtime no longer puts a clock in your prompts

The system prompt carried a runtime-generated date section and a paragraph
explaining the timestamp prefix on user messages. Both are gone. The system
prefix is now byte-stable across turns, which is what provider prompt
caching keys on — a date that changes at midnight invalidates the cached
prefix for every session that spans it.

Calendar guidance belongs in `AGENTS.md` or a tool, where it is written once
and stays put. The same applies to channel prompts: a date section in the
base prompt is left exactly as the workspace wrote it, and history turns are
stored without a runtime wall-clock prefix.

If you relied on the model seeing today's date, say so in `AGENTS.md`.

### A pairing code no longer outgrows its box

`zeroclaw gateway get-paircode` drew the code inside a box hard-coded to
fourteen columns. A longer generated code overflowed it and the right border
sat in the wrong place. The box is now sized to the code.

### Fixed defects

- **The trim breadcrumb lost its ownership across a restart.** The file-backed
  session store never persisted whether a session's transcript started with
  the synthetic trim breadcrumb, so a restarted process could not tell a
  genuine first user turn from machinery, and the transcript was trimmed
  again on every reconnect. The flag is now stored next to the transcript
  (a one-byte sidecar, `1` or `0`). A sidecar holding anything else is
  corruption rather than a value the store ever wrote, and the runtime fails
  closed on it instead of guessing from message text.
- **A restored session replayed one row too few.** The same missing flag made
  the trim count the breadcrumb as a dropped message, so the client replay
  started one turn late. The breadcrumb is now excluded from both the keep-N
  slots and the dropped-message count.
- **A failed Edge TTS read left its temp file behind.** The provider
  reported the read error without removing the artifact it owned, so
  repeated failures filled the temp directory with orphaned media.
- **A process that had already exited was reported as alive.** The
  descendant check used a signal probe, which also succeeds for an unreaped
  zombie; on a host that does not reap orphans promptly the check never
  settled. It now reads the process state from the kernel.
- **The dashboard's session-lifecycle test suite could not mount.** The test
  harness stands in for DOM nodes, and it did not expose
  `getBoundingClientRect`, which the transcript pane reads to decide whether
  to stay pinned to the newest output. Mounting the pane threw, so the whole
  suite — which is what asserts the composer, the message-flow grouping and
  the zero-extra-request rule — failed at once rather than reporting one
  broken assertion. The harness now covers that surface and a test asserts
  it keeps pace with the pane, so a component adopting a new DOM API fails
  one test instead of the file.

## Everything from 1.2.1

1.2.2 contains all of 1.2.1: the effective-context-window fix for the
context meter, the `[context].max_input_tokens` → `[context].request_token_ceiling`
rename, the WASM plugin host, and the restored context engine. See the
[1.2.1 notes](https://github.com/iintothewind/zerolite/releases/tag/v1.2.1) and
the [1.2.0 notes](https://github.com/iintothewind/zerolite/releases/tag/v1.2.0).

`[context].max_input_tokens` is still not accepted — 1.2.2 keeps the
1.2.1 rename.

## Install

| Platform | Asset |
|---|---|
| Windows x64 | `zerolite-1.2.2-x86_64-pc-windows-msvc.zip` |
| Linux x64 | `zerolite-1.2.2-x86_64-unknown-linux-gnu.tar.gz` |
| Linux arm64 | `zerolite-1.2.2-aarch64-unknown-linux-gnu.tar.gz` |

Each binary carries the web dashboard and the WASM plugin host. Verify the
plugin host is present:

```sh
zeroclaw plugin list
zeroclaw status | grep -i plugin
```
