# ZeroLite 1.2.8

The `zeroclaw` CLI on upstream ZeroClaw **v0.8.6**, carrying the fork's context
engine, the WASM plugin host and the web dashboard embedded. Same binary name,
config path and command set. Platforms: Windows x64, Linux x64, Linux arm64.
No macOS build.

Two routing fixes behind one symptom — a session that had uploaded one image kept
answering on a model nobody picked, with a window the config never named — plus a
composer reading that makes throughput visible. No config schema change: an
existing `config.toml` needs no migration.

## The vision detour stops pinning the conversation

A single upload decided every later turn. `[multimodal] vision_model_provider`
routes turns carrying `[IMAGE:]` markers, and route selection counted those markers
across the whole history. After one screenshot, every following turn was re-routed
to the vision provider: its window became the displayed context limit, and the model
chosen in the picker never served again. `max_image_turns` is meant to expire
attachments, but it is read only by request trimming — route selection never
consults it.

Routing now counts markers **this turn introduces**: the latest user message plus the
tool-result carriers after it (`multimodal::count_current_turn_image_markers`).

| Turn content | Route | Behaviour |
|---|---|---|
| a new `[IMAGE:]` marker, primary without vision | vision provider | unchanged: routes to the configured vision route and is metered on its window |
| markers carried over from earlier turns, primary without vision | **the selected model** | new: served by the selected model; markers stripped from the request (what a text-only model can consume), durable history keeps them, so switching back to a capable alias sends the image again |
| no markers, or a primary that accepts images | the selected model | unchanged |

The refusal path is deliberately untouched. With no configured vision provider and a
**loadable** fresh marker on a non-vision primary, the turn fails with
`ProviderCapabilityError`: "received N image marker(s), but this model_provider does
not support vision input", naming the limiting fallback when the primary is a Reliable
aggregate. A silent strip stays forbidden. Markers that parse into nothing (missing
file, remote URL while `allow_remote_fetch = false`) still degrade to text with a WARN.

The reported case: switching from `custom.freellm-gemini-flash-lite-latest`
(1,048,576 → 838,860) back to `custom.freellm-spark1-unsloth` (131,072 → 104,857)
left the ring reading the Gemini pair for every turn — trace evidence was each turn's
served route naming `gemini-flash-lite-latest` while the picker said otherwise. After
this change, from the first post-switch turn the ring reads 131,072 / 104,857.

## A streamed turn publishes the reference it dispatched to

Provider leaves identify themselves by `Attributable::alias` — the bare
`[providers.models.<type>.<alias>]` key, family stripped. The streaming path handed that
leaf-only string downstream where every consumer keys on the config reference: usage
frames' `provider_ref`, the terminal snapshot's provider name, and
`resolved_context_limits_for_route`, which splits on `.` to locate its entry. A bare
alias fails that split, so a vision-routed turn published the 32k unconfigured-window
stub instead of its configured capacity.

- `call_provider` names the exact dispatch route on the streaming accounting scope
  (`with_exact_dispatch_route(active_model_provider_name, active_model)`), as the
  non-streaming path below already does. Inner Reliable/router frames still win over
  this one, so a fallback serving another alias keeps its own identity and capacity.
- `run_tool_call_loop_impl` re-qualifies a served leaf alias that names this
  iteration's own alias back to `<family>.<alias>` (`qualify_served_provider_ref`). Any
  other bare alias is left alone: borrowing the route's family for an unknown alias
  would advertise the wrong model's window.

With both changes, switching back to a text-only model takes effect *and* shows that
model's own numbers.

## The composer reads tokens per second

The stats row gains an `X tok/s` segment reading `TokenRateMeter`: a decay sliding
window over streamed text (three exponential half-lives 5/20/80 s, 250 ms buckets) plus
the history billed by `usage` frames. It sits after cache hit, so the counts prefix
never shifts when the segment appears.

Gate: ≥ 200 estimated tokens over ≥ 4 s of stream. The 1 Hz ticker publishes the reading
while a turn is active; terminal frames publish once and mute it, so the last reading
stays on screen, dimmed. No streamed evidence, no segment — never a `0 tok/s` placeholder.
The first `usage` frame bills the reading, charging the provider's `output_tokens` against
the silent span. Session switch, `clearAllMessages`, `history_trimmed` and unmount zero
the meter.

The cumulative token segments are retired; session totals live in the session dashboard.
Canonical rule: `docs/design/webui.md` → "Composer stats semantics".

  changed (`assets/index-BqayIAk9.js`). A dashboard served from `<data>/web/dist` is
  never used by this build; `embedded-web` outranks it.
- **Verification for this release:** tests run single-threaded (`-- --test-threads=1`), per repo rule. Single-threaded: `zeroclaw-runtime` lib **5,818 passed, 0 failed** (8 ignored), `zeroclaw-providers` lib **1,966** (4 ignored), `zeroclaw-gateway` lib **687**, `zeroclaw-config` lib **1,816**; web suite **202 passed, 0 failed** (node --test plus the jiti suites `pretest` runs) and `npm run typecheck` clean (`check:generated`: 5 pass); `cargo fmt --all --check` clean; no new clippy warnings in the touched files. The parallel run of these crates failed on the documented shared-state set — four providers cases (`openai::tests::responses_*`, `native_tool_round_flags…`, the `grok_cli` fake-child case) and one runtime case (`tools::send_message_to_peer…`) — each passing alone, so those are harness artefacts, not this release's.
- New coverage worth naming: `carried_over_images_keep_the_selected_model` — carried-over markers leave the turn on the primary with stripping, a fresh marker still resolves the vision route without stripping; it **fails before** this change (routing the carried-over case onto the vision provider). `count_current_turn_image_markers_ignores_carried_over_user_images` and `_counts_this_turns_tool_carriers` pin what counts as "this turn". `factory_built_streamed_vision_turn_publishes_config_refs_and_limits` builds the base leaf through the real alias factory over two SSE servers, streams a text turn then an attachment turn, asserts every usage frame carries that route's configured window and budget, both terminals report `<family>.<alias>`, and the limits resolver sees only dotted pair keys (both legs stream: a plain JSON body takes the non-stream recovery path, which applies its own exact route and masks this defect). Three `qualify_served_provider_ref` cases pin qualification of a leaf alias, an already-qualified reference, and a foreign bare alias. Web-side: `tokenRate.test.ts` (gate, decay, terminal mute, first-frame billing) and the session lifecycle/`sessionStats.logic` suites.
- The arm64 binary deployed to the production host was built from this tree before the version bump (`--version` reports 1.2.7; identical sources for both fixes), `embedded-web`, sha256 `13f816c2e5f30ed1…`, 45,328,816 B.
