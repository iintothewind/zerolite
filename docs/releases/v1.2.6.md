# ZeroLite 1.2.6

The `zeroclaw` CLI on upstream ZeroClaw **v0.8.6**, carrying the fork's context
engine, the WASM plugin host and the web dashboard embedded. Same binary name,
config path and command set. Platforms: Windows x64, Linux x64, Linux arm64.
No macOS build.

This release settles the trim semantics: one budget, one action, one place where
the meter moves.

## The context engine

**One number does both jobs.**

```text
trim_budget = min(window × trim_threshold_percent / 100,
                  window − reserve_tokens)      # reserve term omitted when unset
```

The budget is the trigger *and* the fit target. The second number this fork used
to carry — `send_budget = window − reserve_tokens`, fitted after the trim — is
gone. Two numbers made "engage early, fit later" expressible and let a trim
legally stop above the number that would trigger the next one; with one number
the retained history is a function of the same value the operator configured
(decision R9).

**One action at every trigger.** Keep the newest `keep_recent_turns` whole turns
in a single cut, then drop one more turn at a time while the retained request
still exceeds the budget, down to the floor of one (R8). Three shapes were
retired:

| Retired here | Why |
|---|---|
| The per-dispatch *nibble* — drop the single turn that clears the line, re-measure, repeat | Leaves the population just under the budget, so the next turn crosses it again and rewrites the provider prefix. A trim is a cache event; it should happen once, not every turn. |
| The 2/3 shrink for overflow recovery | Not a stronger trim, just a third aggressiveness. Recovery now runs the same action one step deeper than the estimate, because the estimate cannot see an image's real cost or one-time tool schemas. |

Budget-only retention — keep whatever fits the budget, with no `keep_recent_turns`
preference (upstream's `trim_to_recent_turns(budget)`) — stays refused: it makes
retained history a pure function of the budget, so the same conversation keeps
wildly different context on different models.

The config surface is unchanged — four fields, defaults as in 1.2.5:

```toml
[runtime_profiles.coder.context]
request_token_ceiling = 100_000   # optional; clamps the effective window
trim_threshold_percent = 80       # default 80
reserve_tokens = 16_384           # output headroom, optional
keep_recent_turns = 5             # default 5 (clamped 1–10)
```

`send_budget` was a resolved value, never a field; nothing in an existing
`config.toml` needs editing.

**The conservative margin is `11/10`, and the in-turn guard now carries it.**
Every pre-send number is `estimate × 11/10`; where a provider measurement exists
the number is `reported + margin(tail)` instead, and the reported/estimated
ratio is never multiplied into a bound.

## The context meter

The meter moves on four frames, and the client folds all four in **one tested
place** (`web/src/contexts/contextMeter.logic.ts`):

| When | Frame | Label |
|---|---|---|
| A trim lands | `history_trimmed` → `tokens_after` | `estimate` |
| The turn starts, after the budget decision | `context_usage` → `input_tokens` | `estimate`, or `calibrated` when a provider measurement anchors it |
| A provider call returns | `usage` → `input_tokens` | `provider` |
| The turn ends | `done` → `last_input_tokens` | inherited; an explicit `null` clears the numerator |

The trim row is the one with a deadline: it must land *before* the request is
dispatched. The runtime therefore publishes the re-read post-trim estimate on
`context_usage` as well, and a test asserts the two numbers are equal — the
published estimate cannot drift from the notice.

## Fixed defects

- **A trim could land only after the response.** Symptom: just under the line,
  press Enter, the trim fires, and the ring keeps the pre-trim number until the
  provider replies. The in-turn guard priced the request with a number *weaker*
  than the one the turn-start check had just used — the raw estimate (no margin)
  when no report existed yet, which is the first request of **every** turn, and
  a ratio fitted on the previous population otherwise. A population in that band
  was dispatched and trimmed only after the provider had answered. The guard now
  anchors on the provider's own measurement and margins only the tail.
- **The meter's frame handling had no coverage.** Four inline handlers in one
  1400-line component, each with its own guard, so nothing could state what the
  ring does with a frame. They are one reducer now, tested: a trim moves the
  ring at trim time, and `done` cannot resurrect a pre-trim figure.
- **The cross-compile's cleanup could not finish.** The build runs as root
  inside its container, so the `target/` it leaves is root-owned and a
  host-side `rm -rf` fails — the reclaim step then errored at the end of a
  successful build. It now removes that residue from inside a local container
  image (`$ZEROCLAW_RUST_IMAGE`, else `zeroclaw-test`, else `rust:1-bookworm`);
  no image is pulled for it.

## Behaviour changes to know

- **Capacity is compared in the same conservative units as the budget.** A
  population whose margined size exceeds the model window fails closed with a
  typed error, even when the raw estimate fits it exactly. The trade is
  availability: a request within the margin of capacity is refused instead of
  sent. It is accepted because the raw estimator is known to under-count, a
  refusal is diagnosable, and a mid-reply stall is not.
- **A retention may land above the budget at the floor.** The cascade stops at
  `kept_turns == 1`; that is a soft floor — the turn is dispatched — and only a
  population the model window cannot take is a hard failure.

## Upgrading

- No config migration. The four `[context]` fields keep their names, ranges and
  defaults.
- The dashboard's ring now reads **`trim budget`** where it read `trim trigger`;
  the i18n key is `agent.context.ring_detail_trim_budget`. A browser showing the
  old wording is running a bundle from before this build: hashed assets are
  immutable for a year, so hard-reload the tab (no service worker is
  registered).
- A stale dashboard on disk (`~/.local/share/zeroclaw/web/dist`, an installer
  leftover) is never served by this build — `embedded-web` outranks it. Deleting
  it is housekeeping, not a fix.
